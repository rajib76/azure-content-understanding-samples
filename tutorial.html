Azure Content Understanding

Content Understanding Field Guide

Turn documents into structured fields you can hand to anything downstream. Two ways to do it: a prebuilt analyzer, or your own schema. Every output below is from a real run.

How it fits together

You send a document in. An analyzer turns it into typed fields. What comes back is plain JSON, so the same result feeds a database, a search index, an approval workflow, or a dashboard without anything in between knowing it came from a PDF.

1

Run a prebuilt analyzer

There are 88 ready-made analyzers on a fresh resource: invoices, receipts, contracts, ID documents, US tax forms, mortgage packets, plus audio and video. Nothing to define — name one and send a file.

analyze
python analyze_document.py samples/invoice_usd.pdf prebuilt-invoice

# the call underneath
poller = client.begin_analyze_binary(
    "prebuilt-invoice", pdf_bytes, content_type="application/pdf")
result = poller.result()

It returned 31 fields, correct to the cent, including all four line items. It also left gaps — fields its fixed schema simply doesn't have.

2

Run a custom analyzer

A custom analyzer reuses a prebuilt base for OCR and layout, and replaces the field list with yours. The only real decision per field is which of three methods it uses.

extract

Copies text that is literally on the page. Comes back with one span and a bounding box, so you can point at where it came from.

generate

Writes something not present in the document — a summary, an inferred currency code.

classify

Picks one value from an enum you supply.

Pick the method before you polish the description

An EXTRACT field with nothing to copy returns empty no matter how well you describe it. Our Currency field stayed blank until we switched it to GENERATE — the invoice writes $4,153.97 and never says "USD".

create_analyzer.py — one field of each kind
"ShippingAmount": ContentFieldDefinition(
    type=ContentFieldType.NUMBER,
    method=GenerationMethod.EXTRACT,
    description="Shipping or freight charge. Digits only.",
    estimate_source_and_confidence=True,
),
"Currency": ContentFieldDefinition(
    type=ContentFieldType.STRING,
    method=GenerationMethod.GENERATE,
    description="ISO 4217 code. Infer from the symbol and vendor country.",
),
"DocumentType": ContentFieldDefinition(
    type=ContentFieldType.STRING,
    method=GenerationMethod.CLASSIFY,
    description="What kind of commercial document this is.",
    enum=["invoice","creditMemo","purchaseOrder","receipt","other"],
),
create, then use
python create_analyzer.py --recreate
python analyze_document.py samples/invoice_usd.pdf custom_invoice_extended

Confidence is not comparable between analyzers

On the same file, prebuilt-invoice scored 0.31–0.43 while the custom schema scored 0.72–0.99 — every value correct both times. Re-rendering the document with proper typesetting changed nothing, so it is the analyzer, not the document. Worse, the prebuilt's highest scores (0.84–0.97) were all on fields that came back empty. Check whether a value is present before you look at its confidence, and calibrate thresholds per analyzer.

The same analyzer on a spreadsheet

Nothing about the analyzer is PDF-specific. Point it at an .xlsx and the base stage reads the sheet into markdown tables, then your identical field schema runs over that. No new analyzer, no code change — only the file extension differs.

Formulas are not evaluated — cached values are read

A first attempt returned every text field but no totals, and the summary said "total due not stated". The cells held =SUM(E14:E18) with no cached result, so the markdown came back as <td></td> — there was genuinely nothing to extract. Excel caches computed values when it saves, so files from real users are fine; files generated by a script may not be. If totals come back empty, open the sheet and check the cell actually holds a number.

Setup, once per resource

Content Understanding borrows model deployments from your Foundry resource rather than hosting anything, so you tell it which deployment serves which model name. This is saved on the resource, not in your repo.

setup and inspection
# one time — writes the model mapping
python create_setup.py

# read-only, bills nothing
python show_defaults.py
python show_analyzer.py --list
python show_analyzer.py prebuilt-invoice --fields

Prebuilt analyzers ask for an alias — prebuilt-analyzer-completion — rather than a model name, which is what lets one analyzer definition work on any resource. Your custom analyzer names gpt-5.4 directly. Both resolve through the same mapping.
